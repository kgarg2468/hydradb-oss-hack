- **The benchmark found a real engine cliff, and it is the most useful thing we learned.** Id-anchored reads are flat with corpus size (`repos_resolving_version`: 3.8 ms at 100 repos / 0.95M edges → 9.0 ms at 250 repos / 2.36M edges). The two-pattern join `repos_resolving_package` is 31.6 ms → **5,164 ms** over the same step: 163x for 2.5x the data (that pair is the best-of-3 component timing; the end-to-end p95 ratio over the same step is 145x — don't mix them). Bisected since: linear or better to 100 repos, knee between 100 and 150, then it keeps degrading rather than stepping to a new plateau. Not node degradation (every smaller corpus re-measured unchanged on the loaded node) and not memory pressure (4.0 of 7.65 GiB; latency spread 1.3%, far too tight for I/O). Cost tracks the number of `Ver` nodes the first pattern binds — `left-pad` (1 version) 89 ms, `debug` (17) 5,311 ms. Engine timeout messages name `cypher_relationship_edge_records` and `cypher_metadata_hydration`.
- **Why that finding stings and why it matters:** the degrading shape is the one that produces the *negative* ("you resolved chalk 5.6.0, pinned four days before the attack") — the console's single most valuable output. Fix in flight on `perf/anchored-fanout`: resolve the package's version ids with a one-hop id-anchored read, then fan out `repos_resolving_version` per id. The hazard is truncation semantics — `truncated` must OR across every read in the fan-out (including the version-list read) and the row cap must apply to the merged set, or a fan-out silently converts a cut read into a clean negative.

- **The fan-out fix was built, measured, and rejected — this is the important correction.** `perf/anchored-fanout` (version-list read + one id-anchored read per version) is a REGRESSION at N100 (43.4 vs 30.6 ms; 17 extra round trips on a client with no keep-alive) and makes NO difference at N250 (3,727 vs 3,693 ms). Identical rows both ways (392 / 988), so it is purely a perf verdict. Why: anchored reads over `debug`'s 17 versions at N250 cost 46–417 ms each and **the ones returning ZERO rows still cost 65–220 ms** — the cost is expanding a large relationship type from a bound node, and an id entry point does not avoid it. The two-pattern join was a symptom, not the disease. Branch kept locally, NOT merged.

- Mutation idioms that HydraDB actually executes (hard-won, encode everywhere):
  - nodes: `UNWIND $rows AS row MERGE (n {id: row.id}) SET n:Label, n.prop = row.x`
  - edges (production, repeatable): `UNWIND $rows AS row MATCH (s:L1 {id: row.s}), (d:L2 {id: row.d}) MERGE (s)-[e:REL {id: row.id}]->(d) SET e.p = row.p` — MERGE pattern carries ONLY `id`, everything else in a trailing SET. Idempotent + closes intervals in place; 8.1k edges/s.
  - edges (one-shot fixtures only): `… CREATE (s)-[:REL {id: row.id, ...}]->(d)` — faster (12.1k edges/s) but duplicates on re-run. Edge `id` REQUIRED either way.
  - rejected: multi-node CREATE, non-UNWIND MATCH..CREATE, multi-hop CREATE patterns.
